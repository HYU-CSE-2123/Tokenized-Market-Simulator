# AI 활용 경험 — 프로젝트 맥락 관리와 독립 검토 절차

> 작성 기준일: 2026-09-12
> 용도: AI 활용 과정의 사실 기록 및 포트폴리오·자기소개서·면접 자료
> 범위: Codex를 활용한 개발 운영 방식. 향후 계획과 검증된 결과를 구분한다.

## 1. 경험 요약

Tokenized Market Simulator 개발에서 기존 프로젝트 문서와 테스트를 기반으로, 구현 에이전트와 검토 에이전트의 역할을 분리하는 문서 기반 경량 하네스를 구성했다. 작업 시작 시 맥락 확인, 구현과 검증, 독립 검토, 수정·재검토, 결과 기록을 하나의 절차로 연결했다.

여기서 하네스 구성은 기존 Codex 실행 환경 위에 프로젝트별 지침·역할·완료 기준을 추가했다는 의미다. 모델 호출 루프, 도구 실행기, 샌드박스나 에이전트 플랫폼 자체를 새로 개발한 범위는 아니다. RAG나 CI 기반 검토 강제 장치도 구축하지 않았다.

## 2. 도입 배경

프로젝트는 Solidity 컨트랙트, Spring Boot 백엔드, PostgreSQL, web3j, WebSocket이 연결된 구조다. 개별 기능이 동작해도 주문 상태·잔고·온체인 정산·사용자 알림 사이의 일관성이 깨질 수 있어, 구현 결과를 여러 관점에서 확인할 필요가 있었다.

이미 `claude-docs`에는 공통 맥락과 구현 이력, 문서 우선순위, 검증 결과 기록 규칙이 있었다. 따라서 기존 체계를 유지하면서 구현자와 별개의 검토 절차를 보완하기로 했다. 이는 확인된 운영 필요에 대한 설계 판단이며, 기존 방식에서 특정 결함이 발생했다거나 생산성이 낮았다는 측정 결과를 의미하지 않는다.

## 3. 검토한 선택지와 결정

| 선택지 | 판단 | 적용 상태 |
| --- | --- | --- |
| 기존 문서를 활용한 맥락 관리 | 현재 저장소의 문서와 코드 검색을 우선 활용 | 기존 체계 유지 |
| 문서 기반 하네스 보완 | 이미 있는 시작·검증·기록 규칙에 검토 절차 연결 | 적용 |
| 별도 검토 에이전트 | 구현자의 설명뿐 아니라 실제 코드와 요구사항을 독립적으로 확인 | 지침 작성 및 첫 문서 검토 수행 |
| RAG | 자료 증가나 검색 누락 문제가 확인될 때 필요성 재평가 | 미구축 |
| CI·실행 스크립트로 검토 강제 | 실제 운영에서 필요성이 확인되면 검토 | 미구축 |

RAG를 제외한 것은 기술적으로 불가능해서가 아니라, 현재 요구를 기존 파일 검색과 문서로 충족할 수 있다고 판단했기 때문이다. 검색 성능 비교 실험을 수행한 것은 아니다.

## 4. 실제 구성

| 파일 | 역할 |
| --- | --- |
| [AGENTS.md](../AGENTS.md) | 프로젝트 진입 지침. 기존 공통 문서와 검토자 지침으로 연결 |
| [공통 지침](README.md) | 기존 맥락 관리 절차에 검토 대상·인계 정보·재검토·완료 보고 규칙 추가 |
| [검토자 지침](reviewer.md) | 읽기 전용 역할, 도메인별 기준, 근거를 포함한 보고 형식 정의 |
| [구현 로그](implementation-log.md) | 변경·검증 이력에 검토 결과와 미해결 사항을 함께 기록 |

```text
요구사항·프로젝트 맥락 확인
          ↓
구현 및 변경 범위에 맞는 테스트
          ↓
별도 에이전트의 독립 검토
          ↓
지적 근거 확인 → 필요한 수정·검증·재검토
          ↓
검증 결과·검토 결과·남은 작업 기록
```

검토는 기능 구현, 버그 수정, 동작에 영향을 주는 리팩터링, 에이전트 작업 절차 변경을 단위로 수행한다. 단순 질의나 오탈자 수정에는 생략할 수 있다.

검토자에게는 원래 요구사항, 완료 조건, 이번 변경의 파일·diff와 새 파일, 관련 문서, 실행한 검증 결과를 전달한다. 기존 사용자 변경을 이번 작업으로 오인하지 않도록 범위를 구분한다. 검토자는 직접 수정하지 않고 문제의 위치·발생 조건·영향·근거를 보고하며 구현자가 수정한다.

최초 검토 후 재검토는 최대 2회로 제한했다. 별도 검토 기능이 없으면 자체 점검을 수행하되 독립 검토가 실행되지 않았음을 명시한다. 검토 의견이 없더라도 테스트 실패나 미실행 검증이 해소되는 것은 아니다.

## 5. 프로젝트에 맞춘 검토 기준

범용적인 코드 스타일 검사에 더해 다음 도메인 기준을 정의했다. 이는 검토 기준을 마련했다는 의미이며, 아래 항목을 이번 작업에서 모두 재검증했다는 뜻은 아니다.

- 동일 receipt의 중복 처리와 재시도 시 체결·잔고 반영의 멱등성
- 주문 실패 시 잠금 자산 해제와 DB·온체인 상태 불일치 복구
- 토큰 수량 단위, 소수점·반올림, 수수료와 접근 제어
- 개인 WebSocket 구독의 사용자 격리와 공개 payload의 정보 노출
- DB commit 이후 이벤트 발행 및 rollback 시 미발행
- 관련 기능 개발 시 가격 신선도·외부 API 장애와 모의/실제 모드 경계
- 클라이언트 연결 작업 시 재연결·복귀 후 REST 재동기화

## 6. 사람과 AI의 역할

사용자는 AI 활용 방식을 개선하자는 목표를 제시하고, 기존 공통 지침과 제안의 중복을 짚어 도입 범위를 축소했다. 기존 문서를 유지하면서 별도 검토자를 추가하는 방향을 선택했다.

Codex는 저장소 문서와 변경 상태를 확인하고 공통 지침 보완 및 검토자 문서 작성을 수행했다. 별도 검토 에이전트는 작성된 문서의 요구사항 충족 여부, 모순, 실행 가능성과 반복 호출 위험을 확인했다.

따라서 이 경험에서 사용자의 기여는 도입 목적·범위 결정과 기존 개발 흐름에 맞춘 방향 조정이며, 문서 작성과 검토에는 AI를 활용했다. 전체 내용을 수작업으로 작성했다고 표현하지 않는다.

## 7. 실제 수행한 첫 검증

2026-09-12에 새 지침 자체를 대상으로 별도 검토를 수행했다.

- 대상: `AGENTS.md`, 공통 지침 변경, 검토자 지침, 구현 로그의 신규 기록
- 별도 검토자: `review_guidelines`
- 결론: 발견된 필수 수정 없음
- 선택 제안: 검토 결과만 로그에 옮기는 작업의 재검토 예외를 명시하면 반복 해석을 줄일 수 있음
- 처리: 기존의 동작에 영향 없는 문서 수정 생략 규칙을 적용하고 기록의 일치는 구현자가 확인
- 구현자 검사: Markdown 파일 링크 검사와 `git diff --check` 통과
- 애플리케이션 테스트: 문서만 변경했으므로 이번 작업에서는 실행하지 않음

확인된 성과는 공통 지침 연결과 독립 검토 절차 구성, 실제 별도 문서 검토 1회 수행이다. 이후 기능 개발에서의 반복 운영, 버그 감소율, 개발 시간 단축이나 토큰 비용 개선은 아직 측정하지 않았다. 이 경험 기록 문서는 첫 검토 이후 작성했으며 그 검토의 대상은 아니다.

## 8. 한계와 이후 관찰 항목

문서 지침은 에이전트의 실행 절차를 안내하지만 CI처럼 검토 누락을 기계적으로 차단하지 않는다. 별도 맥락의 검토자도 같은 오류를 놓칠 수 있으므로 실제 테스트와 실행 결과를 함께 확인한다.

향후 기능 개발 시 다음을 기록해 도입 효과를 판단한다. 현재 수치는 미측정이다.

| 관찰 항목 | 기록할 내용 |
| --- | --- |
| 검토 실행 여부 | 대상 작업 수, 실제 별도 검토 수, 미실행 이유 |
| 검토의 유효성 | 근거가 확인되어 수정한 지적과 수용하지 않은 지적의 이유 |
| 반복 비용 | 재검토 횟수, 검토 소요 시간, 확인 가능한 토큰 사용량 |
| 완료 이후 품질 | 이후 발견된 회귀와 검토에서 놓친 조건 |

## 9. 포트폴리오·면접 표현 예시

### 이력서용

> Codex 기반 개발에서 기존 프로젝트 문서와 테스트를 연결한 경량 에이전트 하네스를 구성했습니다. 구현·검토 역할을 분리하고, 도메인별 검토 기준과 수정·재검토 및 미검증 사항 기록 절차를 정의했으며, 별도 에이전트로 지침의 첫 검토를 수행했습니다.

### 면접용

> 처음에는 RAG나 별도 하네스 도입을 검토했습니다. 저장소를 확인해 보니 이미 맥락 복원과 검증 기록 규칙이 있어, 기존 체계를 유지하고 독립 검토 절차를 보완하는 것으로 범위를 정했습니다. 검토자에게 실제 변경 코드와 요구사항을 함께 제공하고 주문 정산의 멱등성, 사용자 격리 같은 프로젝트 기준을 확인하도록 했습니다. 현재는 지침 구성과 첫 문서 검토까지 수행했으며, 생산성이나 결함 감소 효과는 이후 기능 개발에서 측정할 계획입니다.

표현 범위는 문서 기반 경량 하네스 구성과 독립 검토 절차 도입이다. 자체 에이전트 엔진 개발, RAG 구축, 완전 자동 품질 보증, 검증되지 않은 정량 성과로 확대해 서술하지 않는다.
